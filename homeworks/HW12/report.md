# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Использовался датасет `S12-hw-dataset.csv`: скалярный ряд `target` (почасовые значения), прогноз на **1 шаг вперёд** (horizon = 1).
- Разбиение **train / validation / test** выполнено **строго по времени**: первые 70% индексов — train, следующие 15% — validation, последние 15% — test (без перемешивания).
- Сравнивались **B1** (naive-last), **B2** (скользящее среднее за 7 часов), **B3** (Ridge на лагах и rolling-признаках), **R1** (однослойная GRU по окну из 24 последних значений ряда).
- Лучшая модель по **val MAE** в последнем прогоне — **R1 (GRU)**; наивный **B1** был близок по val. Итоговые **test**-метрики в `runs.csv` заполнены **только для лучшей** модели (**R1**), остальные строки — только validation.

## 3. Данные и постановка задачи

- Датасет: `S12-hw-dataset.csv`
- Целевая колонка: `target`
- Частота временного ряда: почасовая (1 час между шагами)
- Горизонт прогноза: 1 шаг (1 час)
- Размер датасета: 4320 наблюдений
- Диапазон дат: с 2025-01-01 00:00:00 по 2025-06-29 23:00:00
- Есть ли дополнительные внешние признаки: в исходном CSV только `date` и `target`; для B3 добавлены признаки из самого ряда (лаги, rolling, день недели)
- Комментарий: ряд выглядит нерегулярным по амплитуде; явных пропусков в `date`/`target` нет. Для краткосрочного горизонта сильный «наивный» baseline (повтор последнего значения) часто конкурентоспособен, если ряд не сильно сглаживается усреднением — что и видно по сравнению с B2.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- Как именно выполнен `train / validation / test`: по **растущему времени**: индексы `0 … n_train-1` — train, `n_train … n_train+n_val-1` — validation, остальное — test.
- Какие доли или интервалы использовались: **70% / 15% / 15%** от длины ряда (хронологически).
- Почему `random split` здесь некорректен: случайное разбиение смешивает прошлое и будущее и даёт завышенно оптимистичные метрики; для оценки качества прогноза «вперёд» нужно разделять выборки по времени.

### 4.2. Признаки для baseline-моделей

- Какие лаги использовались: **1, 7, 14** часов
- Какие rolling-признаки использовались: **среднее** и **стандартное отклонение** по окну **7** (по сдвинутому ряду, чтобы не подглядывать в текущий `target`)
- Какие календарные признаки использовались: **день недели** (`dayofweek`)
- Как обрабатывались пропуски после построения лагов/rolling: строки с NaN после сдвигов/rolling **исключались** из обучения Ridge; для `rolling_std_7` начальные NaN после `std()` **заполнялись нулём**
- Использовалось ли масштабирование и где именно оно обучалось: **StandardScaler** для признаков X и целевого y **только на train**-части таблицы признаков (B3); для GRU — **StandardScaler только на train-целевом** фрагменте ряда

## 5. Модели и эксперименты (B1, B2, B3, R1)

Опишите коротко и сопоставимо:

- B1 (`naive-last`): прогноз = значение ряда на предыдущем шаге (`shift(1)`).
- B2 (`moving-average`): прогноз = среднее за **7** предыдущих наблюдений (скользящее среднее с `shift(1)` в построении).
- B3 (`ridge-lag-features`): **Ridge** (alpha=10) на векторе признаков из лагов, rolling mean/std и дня недели; после масштабирования предсказание делается через `np.dot(X, coef) + intercept` (устойчивее к матричному умножению на части macOS).
- R1 (`gru-forecast`): однослойная **GRU** (hidden=48), вход — окно **24** последних значений ряда (после масштабирования целевого ряда на train), выход — прогноз на следующий шаг.

Дополнительно:

- Основная метрика выбора лучшей модели: **MAE на validation**
- Дополнительные метрики: **RMSE**, **MAPE** (на тех же масках конечных значений)
- `window_size` для `GRU`: **24**
- Batch size: **64**
- Максимальное число эпох: **5** (режим `FAST_DEV_RUN=True` в `hw12_run.py`; для финального отчёта при желании увеличьте эпохи и выставьте `FAST_DEV_RUN=False`)
- Optimizer: **Adam**
- Learning rate: **0.001**
- Как сохранялась лучшая модель: веса с минимальной **val MAE** по эпохам, сохранение в `./artifacts/best_gru.pt`, конфиг в `./artifacts/best_gru_config.json`

## 7. Анализ

Наивный прогноз B1 оказался **сильным baseline** на этом горизонте. B2 (moving average) **сильно ухудшил** метрики — сглаживание по 7 часам плохо совпадает с one-step таргетом. Ridge на признаках B3 дал **умеренное** качество и не обошёл B1 на val. **GRU (R1)** в последнем прогоне дала лучшую val MAE среди всех экспериментов: окно из 24 шагов улавливает локальную динамику; обучение с `shuffle=False` в `DataLoader` сохраняет временной контекст батчей. Тренд и сезонность частично отражаются календарным признаком (B3) и окном (R1). Утечки данных минимизируются: split по времени, rolling/лаги только из прошлого, скейлеры fit только на train. Выбор лучшей модели по **validation**, а не по test, нужен, чтобы test оставался **однократной** честной оценкой.

## 8. Итоговый вывод

В качестве базового подхода для такой задачи разумно начинать с **наивных baseline** (B1, B2) и **временного split**. Простого baseline на табличных признаках (B3) часто достаточно, если нужна интерпретируемость и быстрый цикл. К **GRU** имеет смысл переходить при более длинном горизонте, сложной нелинейной динамике или когда больше данных/регуляризации и эпох. Главное: **не перемешивать временные** точки при валидации и **не подбирать гиперпараметры по test**.
