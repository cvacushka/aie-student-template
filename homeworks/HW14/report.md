# HW14 – эмбеддинги, FAISS, оценка retrieval и mini-RAG по базе знаний

Материалы семинара на GitHub: [mirea-aie-2025/aie-course-meta/seminars/S14](https://github.com/mirea-aie-2025/aie-course-meta/tree/main/seminars/S14).

## 1. Кратко: что сделано

- База знаний: **15** коротких текстов про **Git и GitHub** из локального файла `knowledge_base.json` (одна предметная область, воспроизводимая загрузка).
- Чанкинг: символьное окно **480** символов, перекрытие **90**; получено **47** чанков до обновления и **62** после добавления трёх документов.
- Векторизация: **TF-IDF** (`max_features=4000`, биграммы) и **L2-нормализация**; поиск по **косинусному сходству** через **FAISS IndexFlatIP**.
- Контрольная оценка retrieval на **10** запросах при `k=5`: **hit@5 = 1.0**, **recall@5 = 1.0**, **MRR@5 = 0.925** (см. `./artifacts/retrieval_eval.csv`).
- Эксперимент: сравнение **`top_k=3` и `top_k=5`** — при `k=3` **hit@3 = 0.9**, при `k=5` метрики совпадают с основным прогоном.
- Обновление базы: добавлены **3** документа (pre-commit, Git LFS, Conventional Commits), выполнены повторный чанкинг, обучение векторизатора и индексация; в `./artifacts/retrieval_before_after_update.csv` видно смещение топа для запросов по новым темам.
- Mini-RAG: **extractive**-ответ по top-k чанкам с перечислением источников; примеры в `./artifacts/rag_examples.csv`.

## 3. База знаний и подготовка документов

- Предметная область: **система контроля версий Git и работа с GitHub** (клонирование, ветки, PR, CI, теги и т.д.).
- Источник документов: файл репозитория `homeworks/HW14/knowledge_base.json` (поля `documents` и отдельно `documents_update` для этапа обновления).
- Число исходных документов: **15**.
- Число чанков после разбиения: **47** (до обновления), **62** (после добавления **3** документов).
- Какой способ чанкинга использовался: **скользящее символьное окно** с фиксированным шагом `chunk_size - overlap`.
- Основные параметры чанкинга: **`chunk_size=480`**, **`overlap=90`**.
- Комментарий (3-6 предложений): тексты достаточно плотные и терминологически однородные, поэтому по ним естественно формулировать вопросы на поиск фрагмента регламента. Чанки фиксированной длины иногда режут связные абзацы, но для учебного dense retrieval этого достаточно. После расширения базы появляются отдельные «якорные» документы (например, про **Git LFS**), что позволяет увидеть эффект переиндексации на запросах, которых не было в исходном корпусе.

## 4. Retrieval и индекс

### 4.1. Эмбеддинги и индекс

- Какая embedding-модель или способ векторизации использовались: **TF-IDF** по символьным чанкам (`TfidfVectorizer`, до **4000** признаков, **(1,2)**-граммы), векторы **L2-нормализованы**; сходство — скалярное произведение нормированных векторов (**косинус**).
- Какая метрика сходства использовалась: для ранжирования в FAISS — **inner product** по **L2-нормализованным** векторам (эквивалент **косинусному** сходству).
- Какой индекс `FAISS` использовался: **`IndexFlatIP`** (точный перебор, учебный масштаб).
- Какой `top_k` использовался по умолчанию: **5** для основной оценки и **4** для mini-RAG.
- Что показали первые примеры retrieval: для формулировок в терминах Git в топе оказываются ожидаемые `doc_id`; часть запросов по синонимам даёт смешение с близкими по лексике заметками (например, «клонирование» может подтягивать смежные темы вместе с **doc_01**).

### 4.2. Контрольные запросы и оценка retrieval

- Сколько контрольных запросов использовалось: **10**.
- Что считалось релевантным ответом: наличие чанка из документа с идентификатором **`expected_source`** среди **top-k** результатов (**по `doc_id` чанка**).
- Какие метрики retrieval считались: **`hit@k`**, **`recall@k`** (при одном релевантном документе совпадают), дополнительно **`MRR@k`** в ноутбуке.
- Итоговый `hit@k`: при **`k=5`**: **1.0** (см. `./artifacts/retrieval_metrics_summary.json`).
- Итоговый `recall@k`: при **`k=5`**: **1.0**.
- Дополнительные метрики (если были): **`MRR@5` = 0.925**.
- Какие запросы оказались самыми простыми: запросы с уникальными терминами (**stash**, **rebase**, **pull request**) попадают в нужный документ с **ранга 1**.
- Какие запросы оказались самыми проблемными: для формулировки про **клонирование** релевантный **doc_01** оказался на **4-м** месте среди top-5 из-за пересечения лексики с заметками про **удалённые репозитории** и **CI**.

## 5. Эксперимент по параметрам retrieval и обновление базы знаний

- Какой параметр сравнивался (`chunk_size`, `overlap`, `top_k` или другой разумный вариант): **`top_k`**.
- Какие два варианта сравнивались: **`top_k=3`** и **`top_k=5`** при неизменных чанках и TF-IDF.
- Как изменилось качество retrieval: **hit@3 = 0.9**, **hit@5 = 1.0** — один запрос (про клонирование) не попадает в «попадание» при **k=3**, но попадает при **k=5**.
- Какой вариант вы выбрали как основной и почему: **`k=5`** как компромисс между шириной выборки и тем, что для части формулировок нужен **более широкий** топ.
- Что именно было обновлено в базе знаний: добавлены документы **`doc_16`** (pre-commit), **`doc_17`** (Git LFS), **`doc_18`** (Conventional Commits).
- Как была выполнена переиндексация: заново собран корпус чанков, **заново обучен** `TfidfVectorizer` на полном наборе чанков и построен новый индекс FAISS (**обязательно**, так как меняется словарь признаков).
- Что изменилось в retrieval после обновления базы знаний: для запросов про **pre-commit**, **LFS** и **conventional commits** в топе появились новые `doc_id`; для нейтрального запроса про **клонирование** состав топа слегка меняется из-за общей перенумерации и пересчёта весов (см. `./artifacts/retrieval_before_after_update.csv`).

## 6. Mini-RAG и результаты

Ссылки на файлы в репозитории:

- Оценка retrieval: `./artifacts/retrieval_eval.csv`
- Примеры ответов mini-RAG: `./artifacts/rag_examples.csv`
- Сравнение до/после обновления: `./artifacts/retrieval_before_after_update.csv`

Короткая сводка (6-10 строк):

- Контекст для ответа: **4** лучших чанка по TF-IDF + FAISS, объединяемые логикой **extractive**-выбора предложения.
- Способ генерации ответа: **экстрактивный** — выбирается предложение из чанков с максимальным пересечением токенов с вопросом (без LLM).
- Возвращались ли источники вместе с ответом: да, в таблице перечислены **название** и **`doc_id`**.
- На каких вопросах mini-RAG сработал лучше всего: на **stash**, **тегах релиза**, **GitHub Actions** — релевантный документ попадает в топ и формулировка близка к извлечённому предложению.
- На каких вопросах mini-RAG ошибался или отвечал неуверенно: на вопросе с **отрицанием** («**нужен** ли LFS для **маленьких** файлов») извлечённое предложение описывает **установку** LFS, а не отвечает «обычно нет» — ошибка **смысла** при частично верном retrieval.
- Какую роль сыграло качество retrieval: итоговый ответ целиком опирается на попавшие в топ чанки; шум в топе (например, **doc_14** рядом с **doc_16**) смещает extractive-выбор.

## 7. Анализ

Учебная база оказалась удачной: узкая тема и общая терминология дают интерпретируемые ошибки retrieval. Фиксированный чанкинг по символам иногда разрывает связные мысли, из-за чего отдельные запросы требуют большего **k**. Формальные метрики **`hit@k`** и **`recall@k`** хорошо показали разницу между **`k=3`** и **`k=5`** на пограничном запросе про клонирование. Эксперимент с **`top_k`** подтвердил, что уменьшение **k** ужесточает критерий попадания. Обновление базы явно улучшило поиск по **новым** сущностям (**pre-commit**, **LFS**, **conventional commits**), но потребовало **полного** переобучения векторизатора. Типичные ошибки mini-RAG здесь связаны с **extractive**-схемой: отрицания и сравнения «нужно / не нужно» плохо отражаются в выборе предложения, даже если нужный документ найден. Ограничения решения — отсутствие генеративной модели, отсутствие reranking и использование **лексического** TF-IDF вместо семантических эмбеддингов.

## 8. Итоговый вывод

Базовым для такой учебной задачи оставил бы пайплайн: **чистка текста → чанкинг → TF-IDF + L2 → FAISS `IndexFlatIP` → оценка `hit@k`/`recall@k` → обновление корпуса с переобучением векторизатора → extractive mini-RAG с источниками**. Главное про retrieval: даже при **идеальном** «попадании» документа ранг и ширина **k** влияют на удобство последующего ответа. Главное про связь с mini-RAG: без генерации ответ **не исправляет** логические формулировки вопроса — он лишь **цитирует** найденный контекст, поэтому качество retrieval остаётся верхней границей качества ответа.
